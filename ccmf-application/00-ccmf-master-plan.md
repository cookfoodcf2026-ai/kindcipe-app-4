## 2. 問題陳述

### 2.1 香港家庭面對嘅核心痛點

- 每晚都要諗「今晚食乜」造成決策疲勞
- 煮食決策者、工人姐姐、家人之間存在語言與流程斷層
- 食譜散落喺 IG / YouTube / 截圖 / WhatsApp，難以整理
- 買餸清單同排餐資訊分離，增加重複溝通
- 家庭成員各自睇手機，減少共餐與家庭互動

### 2.2 市場背景

- 香港家庭數量龐大，且智能手機普及率高
- 有工人姐姐或家庭協作需要嘅家庭，對雙語、大字版、簡化流程工具有明顯需求
- 香港本地化、家庭協作、工人姐姐友善嘅 AI 食譜 App 仍然稀缺

### 2.3 情感 Hook

> 「每晚，香港有好多家庭都面對同一個問題：今晚食咩？但真正嘅煮食決策者，往往冇人問過佢哋想食咩。」

---

## 3. 解決方案

### 3.1 核心功能

- IG / YouTube 食譜一鍵匯入
- AI 廣東話排餐與智能食材配搭建議
- 自動購物清單與格價連結
- 家庭群組與排餐審批機制
- 工人雙語模式（廣東話＋印尼語／菲律賓語）

### 3.2 用戶價值

- 減少每日諗食咩時間
- 將食譜、排餐、買餸、家庭協作整合成一個流程
- 幫僱主同工人姐姐用同一套清晰指引溝通
- 提升家庭協作效率與晚餐體驗

### 3.3 產品狀態

- 已完成核心 MVP
- 已有前端 App 與後端 API
- 目前可進行內測、收集反饋、迭代

## 4. 技術架構

### 4.1 現有技術棧

- 前端：React Native（Expo SDK 54）
- 路由：expo-router
- 狀態與 API：tRPC + React Query 5
- 後端：Node.js + tRPC + Drizzle ORM
- 資料庫：PostgreSQL
- 雲端：Railway / 相關後端服務
- AI：Google Gemini API

### 4.2 技術原則

- 先做可用，再做完美
- 所有 AI 與敏感邏輯盡量留在後端
- 不把 API Key 或核心 prompt 暴露喺前端 bundle
- 保持類型安全、可維護、可迭代

### 4.3 風險控制

- 加入 crash 監控與 error boundary
- 降低高頻輪詢與背景耗電
- 圖片與大資料經壓縮／URL 化處理

## 5. 市場與受眾

### 5.1 目標客群

1. 香港家庭煮食決策者
2. 有工人姐姐嘅家庭
3. 想慳時間嘅職場父母
4. 想整理 IG / YouTube 食譜嘅用戶

### 5.2 市場切入策略

- 先做 20-30 個 Beta 家庭試點
- 再擴展到 100 個高黏性種子用戶
- 透過 Facebook 群組、親友推薦、IG / Threads 內容招募
- 以真實用戶故事做下一步公開上線素材

### 5.3 目標市場口徑

- **冷啟動**：種子用戶、留存、回饋
- **CCMF**：Beta 驗證、社會影響、可交付里程碑
- **公開版**：下載、口碑、品牌資產

## 6. 商業模式

### 6.1 收入來源

- 訂閱制
- 導購連結（先驗證點擊與轉化，再談合作）
- 工人模式增值服務

### 6.2 定價策略

- 免費版：基本功能
- 早鳥版：HK$30/月
- 正式版：HK$38/月
- 早鳥版與正式版功能一致，只係價格與優惠期不同

### 6.3 CCMF 申請語境建議

- 唔好過度強調收入預測
- 重點應放喺產品驗證、用戶留存、家庭場景與社會效益
- 導購分潤屬後續商業化方向，不應寫成已落地收入

## 11. 風險管理

| 風險 | 影響 | 應對 |
|---|---|---|
| 開發延遲 | 6 個月內未能完成驗證 | 優先核心功能，延後非核心項目 |
| 用戶獲取成本高 | 難以擴大種子用戶 | 先做 FB 群組、親友推薦、內容引流 |
| 競爭者模仿 | 同類功能被複製 | 以本地化、社群、數據、速度建立護城河 |
| 技術風險 | AI / API 不穩定 | 保留 fallback 與手動流程 |

---

## 12. 結論

Kindcipe 不是單純「食譜 App」，而係一個針對香港家庭同工人姐姐協作場景嘅晚餐作業系統。

本計劃以可驗證嘅 Beta、明確 KPI、保守財務預測、清晰社會價值為核心，適合 CCMF 申請。
